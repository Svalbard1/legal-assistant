# Онбординг бекенда — Лиза и Валя

Проект **legal-assistant**: ИИ-ассистент для юристов банка (RAG: юрист спрашивает → система ищет по документам → отвечает со ссылками на источники). Кейс ПСБ × Changellenge, Hack&Change 2026.

Репозиторий: https://github.com/Svalbard1/legal-assistant.git (публичный).

## 0. Кто в команде и кто за что отвечает

| Человек | Зона | Папка в репо | Ветка |
|---|---|---|---|
| Svalbard1 | ML: поиск по документам + генерация | `ml/` | `ml/svalbard1` |
| **Лиза** | бекенд | `backend/` | `be/liza` |
| **Валя** | бекенд | `backend/` | `be/valya` |
| Гульсым | фронтенд | `frontend/` | `fe/gulsym` |

Правила работы с репозиторием — в корневом `README.md`. Три главных: в `main` только через PR; утром `git pull origin main`; секреты — только в `.env`.

## 1. Разовая настройка Git (~15 минут, один раз)

```bash
git config --global user.name "Имя Фамилия"
git config --global user.email "почта-от-github"       # можно noreply-адрес из Settings → Emails
git config --global credential.helper store
git clone https://github.com/Svalbard1/legal-assistant.git
cd legal-assistant
```

Пароль от GitHub в git **не работает** — нужен токен (PAT): открой https://github.com/settings/tokens/new?scopes=repo&description=legal-assistant, галочка `repo` → Generate token → скопируй сразу (показывается один раз). При первом push: Username — твой ник на GitHub, Password — токен.

Создай свою ветку:

```bash
git switch -c be/liza          # или be/valya
git push -u origin be/liza
```

## 2. Прочитать два документа (до того, как писать код)

1. **`ml/docs/API_CONTRACT.md`** — контракт ML-сервиса v0.1: эндпоинты `/health`, `/ingest`, `/ask`, коды ошибок, таймауты, лимиты.
2. **`ml/docs/BACKEND_INTEGRATION.md`** — гайд по интеграции: подъём ML-сервиса за 5 минут, готовый httpx-сниппет, env-переменные, docker-compose, чеклист приёмки, таблица «чей баг».

## 3. Первое практическое задание — прогнать чеклист стыковки

Подними ML-сервис у себя (команды в BACKEND_INTEGRATION.md, раздел 0) и прогони **чеклист приёмки из раздела 6** (10 пунктов). Результат — сообщение в чат команды: какие пункты зелёные, какие нет. Это знакомство и с проектом, и с контрактом, и с тем, как выглядит работа со стыком.

## 4. План работ бекенда

**Фаза 1 — скелет (первая неделя):**
- папка `backend/`: FastAPI-приложение, свой `/health`, свой `requirements.txt`, свой venv
- `docker-compose.yml` в корне: сервисы backend + ml-service (фрагмент для ml готов в гайде, раздел 5; для compose нужен установленный Docker)
- `.env.example` с пустыми значениями (коммитится; сам `.env` в git не попадает)

**Фаза 2 — ядро:**
- регистрация/логин (сессии или JWT), rate-limit
- `POST /api/documents`: приём файла → MinIO → вызов ML `POST /ingest` по контракту (собственный лимит бекенда ≥ 25 МБ)
- `POST /api/ask`: авторизованный запрос → вызов ML `/ask` → сохранение вопроса, ответа и `sources` в PostgreSQL
- обработка недоступности ML (502/504 с понятным сообщением — пункт 8 чеклиста)

**Фаза 3 — продукт:**
- история диалогов (`GET /api/chats`), статусы индексации документов
- деплой, логи, бэкапы БД

Как поделиться между собой — предложение (можете поменяться между собой, для проекта важно лишь, чтобы у каждой фазы был ответственный):
- **Лиза**: публичный API (`/api/ask`, `/api/documents`) + httpx-клиент к ML
- **Валя**: инфраструктура — docker-compose, PostgreSQL (диалоги, метаданные), MinIO (файлы)

## 5. Ежедневный цикл

```bash
git switch be/liza              # своя ветка
git pull origin main            # свежий main с утра — главное анти-конфликтное правило
# ...работа...
git add -A && git commit -m "backend: что сделано"
git push
```

Готова фича → Pull Request на GitHub (base `main` ← твоя ветка), в описании 2–3 строки: что сделано и как проверить. Ревью: друг у друга; если трогается стык с ML (контракт) — ревью Svalbard1 обязательно. После approve мержишь сама.

## 6. Правила стыка с ML

- Вы **не коммитите** в `ml/`, Svalbard1 не коммитит в `backend/`. Граница папок = граница ответственности.
- Изменения контракта — только PR, меняющий `ml/docs/API_CONTRACT.md` и `ml/service.py` одновременно, с ревью Svalbard1.
- `detail` из ошибок ML можно писать в лог как есть — там человекочитаемое описание.
- Спорные вопросы фиксируются правкой контракта, а не устной договорённостью; вопросы — в общий чат команды.

## 7. Запрещено

- Пушить в `main` напрямую, force-push.
- Коммитить секреты, `venv/`, `node_modules/`, большие бинарники, дампы БД.
- Писать свой поиск/индексацию параллельно с ML — эта зона занята, взаимодействие только через контракт.
