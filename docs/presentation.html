01 · проблема

Юристу нужен не «текст от ИИ», а проверяемое основание

В договоре важны точная редакция, пункт и контекст. Уверенный, но неподтверждённый ответ создаёт риск.

Поиск вручную

Долго листать массив документов

Условия могут быть в разных файлах, редакциях и формулировках.

Обычный чат-бот

Ответ может звучать убедительно

Но без ссылки на первоисточник трудно проверить факт и применимость.

Критерий решения

Каждое утверждение — к фрагменту документа

Если оснований нет — не маскировать пробел догадкой.

Отличие от «сразу спросить LLM»

Генерация получает ограниченный контекст найденных документов, а интерфейс показывает источники рядом с ответом.

Осознанный выбор режима

Без настроенного LLM система работает в stub-режиме: возвращает детерминированную выжимку источников. Внешняя генерация подключается отдельно.

03 · сквозной сценарий

1
Выбирает или загружает документ

Нет оснований в базе — нет выдуманного условия.

На этом golden-наборе 400/50 закрыл промах в топ‑3 и уменьшил размер контекста примерно на 19% относительно 500/50.

Почему не усложняли

Структурный чанкинг с заголовком секции дал тот же recall@3, но более низкие MRR и recall@1 — добавленный заголовок разбавлял эмбеддинг пункта.

07 · надёжность

Когда доказательств мало, интерфейс должен показать границу знания

Штатный сценарий
  • Вопрос проходит строгую валидацию.
  • Поиск возвращает фрагменты документов.
  • Ответ сопровождается источниками и метаданными.
  • История диалога хранится в PostgreSQL.
Нештатный сценарий
  • Пустой индекс → API сообщает, что документы нужно загрузить.
  • Слабый сигнал поиска → отказ, источники при этом доступны для проверки.
  • Сбой внешнего LLM → fallback на выжимку источников.
  • Недоступен ML → Backend возвращает 502/504.

08 · ценность и внедрение

Ценность — сократить путь до нужного пункта, не подменяя решение юриста

Пользователю

Быстрее найти условие и проверить контекст

  • Поиск по смыслу и точным терминам.
  • Источник раскрывается рядом с ответом.
  • История помогает продолжить диалог.
Бизнесу

Потенциал измеряется в пилоте

  • Время до релевантного пункта.
  • Доля ответов с подтверждённым источником.
  • Доля корректных отказов на вопросах вне базы.
  • Доля запросов, требующих ручной эскалации.

09 · статус и следующий шаг

Прототип проверяем; до пилота нужны загрузка через Backend и эксплуатационные контроли

Уже реализовано
  • ML ingestion и поиск по документам.
  • Источники в ответе, сессии и история чата.
  • React-интерфейс, PostgreSQL и миграции.
  • Локальный Docker Compose всего стека.
  • Автономный ZIP-сабмит для платформы.
Ограничения / развитие
  • Публичный hosted demo не развёрнут; база знаний не входит в репозиторий.
  • Загрузка файла из UI ожидает Backend `/api/ingest`, которого пока нет; демо ingest идёт напрямую в ML API.
  • Нет auth/ролей и production-наблюдаемости.
  • Следом: Backend upload, аудит доступа, оценка на разрешённом корпусе и пилот с юристами.
Проверка Docker-инструкции воспроизводится в репозитории; локальный контейнерный запуск в среде подготовки этой презентации не подтверждался из-за отсутствующего Docker Compose plugin.
